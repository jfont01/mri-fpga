Problema corregido en `kv()`
============================

En algunos scripts había una línea inválida de Python por f-string anidado:

    print(f"  {color(f'{key + ':':<24}', C.GRAY)} {value}")

Eso está mal.

Debe usarse:

    def kv(key: str, value: Any) -> None:
        key_txt = f"{key}:"
        print(f"  {color(f'{key_txt:<24}', C.GRAY)} {value}")

Esto debe revisarse en cualquier script que te pase.

Métrica Fmax
============

En los reportes Tcl se escribe:

    CLOCK_PERIOD_NS
    CLOCK_FREQ_MHZ, si aplica
    CLOCK_UNCERTAINTY_NS
    WNS_NS
    WHS_NS
    EST_FMAX_MHZ

Fmax se estima como:

    Tcrit(ns) = Tclk(ns) - WNS(ns)
    Fmax(MHz) = 1000 / Tcrit(ns)

Esto es una estimación derivada del timing, no una frecuencia garantizada final. En síntesis se considera informativa; la frecuencia final debe evaluarse post-route.

En síntesis, `WHS` puede aparecer negativo post-synthesis, pero lo estamos tratando como informativo. El criterio principal de PASS/FAIL en synthesis es setup:

    WNS >= 0

Errores que ya ocurrieron y cómo se resolvieron
===============================================

1. Error:

    'str' object has no attribute 'exists'

Causa típica: una variable de entorno como `RUN_SYNTH_TCL`, `RUN_IMPL_TCL` o `RUN_XSIM_TCL` se tomó como string y luego se llamó `.exists()`.

Corrección:

    run_impl_tcl_env = os.environ.get("RUN_IMPL_TCL")

    if run_impl_tcl_env:
        run_impl_tcl = Path(run_impl_tcl_env).resolve()
    else:
        run_impl_tcl = project_root / "scripts" / "run_impl.tcl"

    if not run_impl_tcl.exists():
        raise FileNotFoundError(...)

Lo mismo para synth y xsim.

2. Error:

    [Errno 2] No such file or directory: 'vivado'

Causa: Vivado no estaba en PATH.

Decisión actual: no usar `shutil.which()` ni `VIVADO_BIN`; dejar `"vivado"` directo y asumir que el entorno ya fue cargado.

3. Error:

    module 'cast_wrapper_impl' not found

Causa: el archivo `implementation/cast_wrapper_impl.v` existía, pero probablemente el módulo interno todavía se llamaba `cast_wrapper_synth`.

Corrección: el top debe llamarse exactamente:

    module cast_wrapper_impl

porque `run_impl.tcl` usa:

    set top_name "${module_name}_wrapper_impl"

4. Error:

    AttributeError: 'ImplResult' object has no attribute 'carry8'

Causa: la tabla imprimía `result.carry8`, pero el dataclass `ImplResult` o alguno de los constructores de `ImplResult` no tenía ese campo.

Corrección: el dataclass debe tener:

    carry8: int | None
    uram: int | None
    bufg: int | None

y todos los lugares que crean `ImplResult`, tanto el caso exitoso como el bloque `except`, deben pasar:

    carry8=as_int(metrics.get("CARRY8")),
    uram=as_int(metrics.get("URAM")),
    bufg=as_int(metrics.get("BUFG")),

5. Problema con métricas viejas

Si Vivado falla antes de correr, el bloque `except` a veces lee reportes viejos con `collect_*_metrics(case)`, y eso puede mostrar WNS/LUT/etc. de una corrida anterior. Esto puede confundir. Si trabajamos sobre ese punto, conviene limpiar reportes del caso antes de correr o marcar explícitamente que las métricas son stale/no válidas cuando falla antes de lanzar Vivado.

Simulador C++ RTL-like: rtlsim
================================

También estoy desarrollando un simulador C++ liviano llamado, por ahora, `rtlsim`.

El objetivo de `rtlsim` no es reemplazar Verilog/SystemVerilog, Vivado XSIM ni un simulador HDL completo. Su objetivo es permitirme modelar arquitecturas RTL-like en C++ de forma rápida para validar:

- organización de pipelines,
- latencias ciclo a ciclo,
- propagación de señales valid,
- comportamiento de registros,
- modelos fixed-point,
- trazas internas,
- primeros prototipos arquitectónicos antes de escribir RTL sintetizable.

Este simulador debe mantenerse simple, explícito y fácil de depurar.

Estructura conceptual de rtlsim
===============================

La librería base está en:

    rtlsim.hpp

En versiones previas se llamó `crtl.hpp`, pero la idea actual es usar el nombre:

    rtlsim

El namespace puede estar todavía como:

    namespace rtl

pero la intención futura es posiblemente renombrarlo a:

    namespace rtlsim

No asumas que ya está renombrado. Primero revisá los archivos que te pase.

Convención de organización de archivos
======================================

Para un módulo de prueba, por ejemplo `AccumulatorPipeline`, queremos separar:

    rtlsim.hpp
        Librería base del simulador.

    accumulator_pipeline.hpp
        Declaración/interfaz del modelo RTL-like.

    accumulator_pipeline.cpp
        Implementación del modelo RTL-like.

    tb_accumulator_pipeline.cpp
        Testbench C++ que instancia el modelo, aplica estímulos,
        corre ciclos de simulación, loguea señales y escribe CSV.

La idea es que el modelo quede separado del testbench, igual que en RTL:

    modelo        -> parecido al DUT
    testbench     -> estímulos, observación, logs, checks

Semántica principal del simulador
=================================

El simulador modela explícitamente registros, wires y puertos.

Registros
---------

Un registro se representa como:

    Reg<T>

y tiene dos campos públicos:

    reg.i    -> próximo valor, equivalente a D
    reg.o    -> valor actual, equivalente a Q

La regla fundamental es:

    reg.i pasa a reg.o solamente en un ciclo de simulación

Es decir:

    o <- i

ocurre cuando el simulador hace commit de los registros.

Antes de evaluar la lógica secuencial, el simulador ejecuta:

    hold_all()

lo que hace:

    reg.i = reg.o

para todos los registros. Esto modela el comportamiento por defecto de mantener el valor anterior si la lógica secuencial no asigna explícitamente un nuevo valor.

Wires
-----

Los wires se representan como:

    Wire<T>

y no tienen `.i` ni `.o`.

Se leen y escriben directamente:

    sum_w = i_a + i_b;

Puertos
-------

Los puertos se separan por dirección:

    InPort<T>
    OutPort<T>

Los puertos también se leen/escriben directamente. No tienen `.i` ni `.o`.

Convención de nombres recomendada
=================================

Usar esta convención en los modelos:

    i_*      -> puertos de entrada
    o_*      -> puertos de salida
    *_w      -> wires combinacionales
    *_r      -> registros

Ejemplo:

    rtl::InPort<int>  i_a;
    rtl::InPort<int>  i_b;
    rtl::OutPort<int> o_sum;

    rtl::Wire<int> sum_w;

    rtl::Reg<int> sum_r;

Modelo de módulos
=================

Todo modelo RTL-like hereda de:

    Module

y puede sobrescribir:

    connect_clocks()
    init()
    combinational()
    sequential()

connect_clocks()
----------------

Sirve para registrar explícitamente qué registros pertenecen al clock domain.

Ejemplo:

    void connect_clocks(rtl::ClockDomain& clk) override
    {
        clk.add(sum_r);
        clk.add(acc_r);
        clk.add(valid_r);
    }

init()
------

Sirve para inicializar el estado de simulación.

Debe usarse para cargar valores iniciales de registros, wires, puertos y salidas.

Ejemplo:

    sum_r.set_initial_value(0);
    valid_r.set_initial_value(false);

    i_a = 0;
    i_valid = false;

combinational()
---------------

Debe modelar únicamente lógica combinacional.

En esta función se pueden asignar:

    wires
    outputs

No debe asignar:

    reg.i

Ejemplo:

    void combinational() override
    {
        sum_w = i_a + i_b;

        o_sum = sum_r.o;
        o_valid = valid_r.o;
    }

sequential()
------------

Debe modelar la lógica secuencial.

En esta función se asignan los próximos valores de registros:

    reg.i

Ejemplo:

    void sequential() override
    {
        sum_r.i = sum_w;
        valid_r.i = i_valid;
    }

Orden de simulación por ciclo
=============================

El simulador ejecuta un ciclo con este orden conceptual:

    1. hold_all()
       Todos los registros copian o en i para mantener valor por defecto.

    2. eval_combinational()
       Se calculan wires y outputs con el estado actual.

    3. eval_sequential()
       Se calculan los próximos valores reg.i.

    4. commit_all()
       Todos los registros actualizan simultáneamente:
           reg.o <- reg.i

    5. eval_combinational()
       Se recalculan outputs y wires después del flanco.

    6. cycle_++

Esto permite que el modelo tenga una semántica parecida a RTL síncrono.

Funciones de simulación
=======================

El simulador tiene:

    cycle()

para simular un ciclo, y:

    cycle(std::uint64_t n)

para simular múltiples ciclos.

Ejemplo:

    sim.cycle();

o:

    sim.cycle(10);

Si se usa `cycle(n)` con trazas, hay que recordar que:

    trace.sample(sim)

después de `sim.cycle(10)` solo registra el estado final,
no los ciclos intermedios.

Para estímulos diferentes en cada ciclo, por ahora conviene mantener un loop explícito en el testbench.

Trazas CSV
==========

El simulador tiene una infraestructura simple de trazas CSV.

TraceFiles crea cuatro archivos:

    in_ports.csv
    out_ports.csv
    wires.csv
    regs.csv

La intención es separar las señales por tipo:

    in_ports.csv   -> entradas del DUT
    out_ports.csv  -> salidas del DUT
    wires.csv      -> señales combinacionales internas
    regs.csv       -> registros internos

Uso típico:

    rtl::TraceFiles trace;

    trace.add_in_port("i_a", dut.i_a);
    trace.add_out_port("o_sum", dut.o_sum);
    trace.add_wire("sum_w", dut.sum_w);
    trace.add_reg("sum_r", dut.sum_r);

    sim.init();
    trace.sample(sim);

    for (...) {
        dut.i_a = ...;
        sim.cycle();
        trace.sample(sim);
    }

`add_reg()` registra por defecto `reg.o`.

También existen o pueden existir:

    add_reg_i()
    add_reg_o()

para registrar explícitamente:

    reg.i
    reg.o

Interpretación de las trazas
============================

Con la convención actual:

    sim.cycle();
    trace.sample(sim);

cada fila registrada después del ciclo 0 representa el estado post-clock de ese ciclo.

Por ejemplo, la fila:

    cycle = 1

contiene:

    entradas aplicadas antes del clock 1,
    wires luego de eval_combinational(),
    registros .o después del flanco,
    outputs después del flanco.

Si más adelante quiero distinguir pre-clock y post-clock, se podría agregar una columna `phase`, pero no quiero agregar esa complejidad todavía salvo que haga falta.

Uso de ap_fixed con rtlsim
==========================

Ya probamos que en mi máquina Linux existe `ap_fixed.h` en:

    /tools/Xilinx/Vitis/2024.2/include/ap_fixed.h

Para compilar con `g++`, conviene usar:

    -isystem /tools/Xilinx/Vitis/2024.2/include

en vez de:

    -I /tools/Xilinx/Vitis/2024.2/include

porque los headers de Vitis generan muchos warnings internos con:

    -Wall -Wextra -pedantic

Ejemplo correcto:

    g++ -std=c++17 -Wall -Wextra -pedantic -O2 \
        -isystem /tools/Xilinx/Vitis/2024.2/include \
        test_ap_fixed.cpp \
        -o test_ap_fixed

Probamos un ejemplo mínimo:

    #include <ap_fixed.h>
    #include <iostream>

    int main()
    {
        ap_fixed<8, 3> x = 1.25;
        ap_fixed<8, 3> y = -0.5;
        ap_fixed<9, 4> z = x + y;

        std::cout << z << "\n";
        return 0;
    }

y produjo:

    0.75

Por lo tanto, `ap_fixed` funciona en C++ para simulación.

Regla importante:

    No incluir <ap_fixed.h> dentro de rtlsim.hpp.

En su lugar, crear tipos fixed-point en otro archivo, por ejemplo:

    fxp_types.hpp

o incluir `ap_fixed.h` directamente en el modelo que lo necesite.

Ejemplo de tipos fixed-point
============================

Para pruebas con fixed-point se propuso algo como:

    using sample_t = ap_fixed<16, 2, AP_RND, AP_SAT>;
    using coeff_t  = ap_fixed<18, 2, AP_RND, AP_SAT>;
    using acc_t    = ap_fixed<40, 8, AP_RND, AP_SAT>;

Interpretación:

    sample_t:
        total = 16 bits
        integer = 2 bits incluyendo signo
        fractional = 14 bits
        signed
        redondeo = AP_RND
        overflow = AP_SAT
        rango aproximado = [-2, 1.99993896]
        resolución = 2^-14

    coeff_t:
        total = 18 bits
        integer = 2 bits incluyendo signo
        fractional = 16 bits
        signed
        redondeo = AP_RND
        overflow = AP_SAT

    acc_t:
        total = 40 bits
        integer = 8 bits incluyendo signo
        fractional = 32 bits
        signed
        redondeo = AP_RND
        overflow = AP_SAT

Test FIR fixed-point propuesto
==============================

Como primera prueba con aritmética fixed-point en `rtlsim`, queremos implementar un FIR pasabajos simple.

Parámetros propuestos inicialmente:

    Fs  = 1 GHz
    Fin = 100 MHz
    Fc  = 90 MHz

El testbench genera una senoidal de entrada de 100 MHz y la pasa por un FIR pasabajos con frecuencia de corte de 90 MHz.

La idea es usar esta prueba para validar:

    1. uso de ap_fixed dentro de Reg/Wire/Port,
    2. propagación ciclo a ciclo,
    3. trazas CSV,
    4. cuantización de coeficientes,
    5. efecto de un filtro fixed-point,
    6. estimación simple de ganancia RMS en régimen estacionario.

El FIR propuesto inicialmente es de 31 taps con ventana de Hamming.

Estructura sugerida:

    fir_lowpass.hpp
    fir_lowpass.cpp
    tb_fir_lowpass.cpp

El modelo conceptual usa:

    InPort<sample_t> i_x
    InPort<bool>     i_valid

    OutPort<sample_t> o_y
    OutPort<bool>     o_valid

    Wire<acc_t> acc_w

    std::array<coeff_t, NTAPS> h

    std::array<Reg<sample_t>, NTAPS - 1> delay_r
    Reg<sample_t> y_r
    Reg<bool>     valid_r

La arquitectura es un FIR directo:

    y[n] = sum_k h[k] * x[n-k]

con:

    throughput conceptual = 1 muestra/ciclo
    latencia visible = 1 ciclo
    multiplicadores conceptuales = NTAPS
    acumulador combinacional = suma de NTAPS productos

Esto todavía no es una arquitectura optimizada para FPGA; es un modelo funcional/arquitectónico inicial. Si luego se quiere llevar a RTL sintetizable, habrá que analizar:

    latencia,
    pipeline de multiplicadores y sumadores,
    uso de DSP,
    ancho del acumulador,
    saturación,
    redondeo,
    throughput,
    frecuencia máxima,
    recursos en Kria KV260/K26.
